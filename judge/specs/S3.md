## The save trigger (binding)

`Page_Load` runs validation and save only when `Request["user_hit_submit"] == "1"` (edit_bug.aspx.cs:100,142-146). Any other POST is treated as the project dropdown's autopostback and only reloads the user dropdown (:133-137).

**No element named or with id `user_hit_submit` exists** in the original:
- edit_bug.aspx doesn't have one.
- EditBug.js:188-190 sets `$("#user_hit_submit")`, which matches nothing.
- EditBug.js:35-38 disables the clicked button and calls `form.submit()`.

So the browser posts the rendered form's successful controls, with no submit button (it was disabled) and no `user_hit_submit`. The original then **saves nothing**. This is pinned as inherited.

The save-path tests add `<input type=hidden name=user_hit_submit value=1>` to the rendered form, which is what the browser would post if the element existed. They submit with **no button name**, because the original never reads the button.

The port must:
1. Accept a `user_hit_submit` form field.
2. Run the save path only when it is `1`.
3. Not require a button name.

## Handles used (binding on the port)

- URL: `edit_bug.aspx?id=N`, where `id=0` means a new bug.
- Field logical names: `short_desc`, `project`, `org`, `category`, `priority`, `assigned_to`, `status`, `comment`, `user_hit_submit`. The hidden `prev_*` and `snapshot_timestamp` fields are carried untouched as plumbing.
- Element ids:
  - `msg`
  - `short_desc_err`
  - `bugid`
  - `submit_button`, whose value is the button label
  - `static_short_desc`, `static_project`, `static_org`, `static_category`, `static_priority`, `static_status`, `static_assigned_to`
- Option lists, as `value=text` pairs in document order, of the `project`, `org`, `category`, `priority`, `status` and `assigned_to` selects.

### 5. `changingStatusAndPriorityUpdatesBugThenFailsOnHistory` (inherited)

The test seeds bug 1, does `GET edit_bug.aspx?id=1`, sets `status=2` and `priority=1`, and posts with `user_hit_submit`.

Expected:
- **HTTP 500.**
- The `bugs` row **was** updated: status 2, priority 1, last-updated user admin, last-updated date in the window, and tags NULL changed to `''`. Other columns are unchanged.
- `bug_posts` is **empty**.

Why: `do_update` commits the `update bugs` statement first (:745-787). `record_changes` then calls `AddChange` (:1743-1756), whose SQL is
`values(@id, @us, getdate(), 'Changed ' + @field + ' from ' + @oldValue + ' to ' + @newValue, 'update'`.
It is missing the closing `)`, so SQL Server raises a syntax error. That exception is unhandled (Global.asax.cs:19-24 only logs it).

The intended history text would have been `Changed priority from low to high` (:1816-1817). The original never stores it. If prompt 06 fixes this, the expected values become that text and a `Changed status from new to in progress` row.

## Normalization beyond README

- **Dates** are compared to a window `[before, after]` taken from the DB server's `getdate()`. The original writes dates with `getdate()`, so the DB clock is the reference clock. Equalities between columns are exact where one `@now` or one statement writes both.
- Full-page text checks for error pages use `contains` on N1-normalized text. Those pages have no element id: the original writes bare HTML and calls `Response.End`. The message text itself must match exactly.

## Not judged, and why

- **The `reported_by` text** ("Created by … N seconds ago") depends on the current time.
- **The page `<title>`, the side-menu links and the prev/next navigation** are layout.
- **The project-dropdown autopostback** that re-filters `assigned_to` isn't covered: the seed has no project-specific exclusions for admin.
- **Optimistic-lock conflict** ("Somebody changed it", :803-809) would need two racing sessions and timing-dependent `snapshot_timestamp` values.
- **Session priming (fixed in the judge).** `ViewStateUserKey = Session.SessionID` (edit_bug.aspx.cs:32) needs the same session ID on GET and POST. ASP.NET InProc issues a new SessionID per request until something is stored in Session. The post-login landing page `bugs.aspx` does **not** store anything (bugs.aspx.cs:14-40 and the `BugList` control, BugList.ascx.cs:13-16, store nothing in Session; the earlier assumption about btnet/bug_list.cs was wrong), so the id=0 postback tests (`createBugRedirectsToItAndWritesRows`, `missingShortDescriptionIsRejected`, `browserPostWithoutUserHitSubmitSavesNothing`) call the core fixture `primeAspNetSession(web)` after login (search postback, `Session["bugs"]`, search.aspx.cs:620). Tests that first GET `edit_bug.aspx?id=N` for an existing bug are already primed: `Session["project"]` is stored at edit_bug.aspx.cs:302.
