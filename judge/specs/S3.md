## The save trigger (binding) — sanctioned fix F1 (RULEBOOK §0.1, D-003)

`Page_Load` runs validation and save only when `user_hit_submit` equals `1`
(edit_bug.aspx.cs:100,142-146); any other POST is the project dropdown's autopostback and only
reloads the user dropdown (:133-137).

The original rendered **no** element named `user_hit_submit` (EditBug.js:188-190 sets
`$("#user_hit_submit")`, which matched nothing), so a browser never saved. The port is
specified as fixed:

1. `did_user_hit_submit_button()` is true iff **any** value of `user_hit_submit` in the query
   string or the form equals `1`.
2. The form renders `<input type="hidden" id="user_hit_submit" name="user_hit_submit" value="1" disabled>`.
3. `#submit_button` (and `#submit_button2` when `DisplayAnotherButtonInEditBugPage=1`, default 0, not
   judged) carries `onclick="document.getElementById('user_hit_submit').disabled=false;"`.

The judge simulates the click (`Scenario.formAfterSubmitButtonClick`): it asserts 2 and 3 on the
rendered page, removes `disabled`, and submits the form as rendered. `Form` skips disabled
controls exactly like a browser, so a form submitted *without* the click posts no
`user_hit_submit`. The older save-path tests still append a literal
`<input type=hidden name=user_hit_submit value=1>` (what the browser posts after the click);
they submit with **no button name**, because the original never reads the button.

## Handles used (binding on the port)

- URL: `edit_bug.aspx?id=N`, where `id=0` means a new bug.
- Field logical names: `short_desc`, `project`, `org`, `category`, `priority`, `assigned_to`, `status`, `comment`, `user_hit_submit`. The hidden `prev_*` and `snapshot_timestamp` fields are carried untouched as plumbing.
- Element ids:
  - `msg`
  - `short_desc_err`
  - `bugid`
  - `submit_button`, whose value is the button label
  - `static_short_desc`, `static_project`, `static_org`, `static_category`, `static_priority`, `static_status`, `static_assigned_to`
- Option lists, as `value=text` pairs in document order, of the `project`, `org`, `category`, `priority`, `status` and `assigned_to` selects.

## Normalization beyond README

- **Dates** are compared to a window `[before, after]` taken from the DB server's `getdate()`. The original writes dates with `getdate()`, so the DB clock is the reference clock. Equalities between columns are exact where one `@now` or one statement writes both.
- Full-page text checks for error pages use `contains` on N1-normalized text. Those pages have no element id: the original writes bare HTML and calls `Response.End`. The message text itself must match exactly.

## Not judged, and why

- **The `reported_by` text** ("Created by … N seconds ago") depends on the current time.
- **The page `<title>`, the side-menu links and the prev/next navigation** are layout.
- **The project-dropdown autopostback** that re-filters `assigned_to` isn't covered: the seed has no project-specific exclusions for admin.
- **Optimistic-lock conflict** ("Somebody changed it", :803-809) would need two racing sessions and timing-dependent `snapshot_timestamp` values.
- **Session priming (fixed in the judge).** `ViewStateUserKey = Session.SessionID` (edit_bug.aspx.cs:32) needs the same session ID on GET and POST. ASP.NET InProc issues a new SessionID per request until something is stored in Session. The post-login landing page `bugs.aspx` does **not** store anything (bugs.aspx.cs:14-40 and the `BugList` control, BugList.ascx.cs:13-16, store nothing in Session; the earlier assumption about btnet/bug_list.cs was wrong), so the id=0 postback tests (`createBugRedirectsToItAndWritesRows`, `missingShortDescriptionIsRejected`, `submitButtonClickCreatesBug`, `projectAutopostbackWithoutButtonClickSavesNothing`) call the core fixture `primeAspNetSession(web)` after login (search postback, `Session["bugs"]`, search.aspx.cs:620). Tests that first GET `edit_bug.aspx?id=N` for an existing bug are already primed: `Session["project"]` is stored at edit_bug.aspx.cs:302.
