# S5 — Bug from e-mail API (`POST api/BugFromEmail`)

Test class: `judge/src/test/java/judge/scenarios/S5_BugFromEmailTest.java`. Lines are relative to `src/BugTracker.Web/` unless the path says otherwise.

## Endpoint and request shape (binding on the port)

- **Route:** `api/{controller}/{id}` → `POST api/BugFromEmail` (App_Start/WebApiConfig.cs:15-19). The path is case-insensitive.
- **Auth:** `[Authorize]`, using the OWIN `ApplicationCookie` that the normal login issues (App_Start/Startup.Auth.cs). The judge logs in with the `loginAdmin` fixture.

  The real client, btnet_service (`src/btnet_service/POP3Main.cs:689-722`), logs in by POSTing `user`/`password` to `api/Login`, keeps the cookie, and then POSTs **form-urlencoded** `projectId`, `fromAddress`, `shortDescription`, `message` (the raw MIME), and optionally `bugId`.
- **Body binding.** The model is `Models/BugFromEmail.cs`:

  | Property | Notes |
  |---|---|
  | `ProjectId` | |
  | `Comment` | |
  | `FromAddress` | `[Required]` |
  | `CcAddress` | |
  | `Message` | |
  | `Attachment` | `byte[]`, base64 in JSON |
  | `AttachmentContentType`, `AttachmentFileName`, `AttachmentDescription` | |
  | `BugId` | int |
  | `ShortDescription` | |
  | `OrganizationId`, `CategoryId`, `PriorityId`, `StatusId`, `AssignedTo`, `UdfId` | nullable int |

  The original binds JSON and form-urlencoded, case-insensitively (Web API defaults). The judge sends JSON with the declared PascalCase names and form fields in the client's camelCase, so the port must accept both.
- **Success response:** `200`, `Content-Type: application/json`, and a body that is the bug id as a bare JSON number (`Ok(int)`, Controllers/BugFromEmailController.cs:177,239).

## Settings relied on

- `StatusResultingFromIncomingEmail=0`: replies don't change the status.
- `TrackingIdString=DO NOT EDIT THIS:`
- `AutoReplyText` is set, but project 1 has no `pj_pop3_email_from`, so no auto reply is sent (Mail/email.cs:372-393).
- `UpdateBugAfterInsertBugAspxSql` is commented out, so `apply_post_insert_rules` is a no-op.
- No subscribers qualify, so no notifications are queued.

## Tests

### 1. `unauthenticatedPostIsRedirectedToLogin`

An anonymous JSON POST hits `[Authorize]`, which returns 401. The OWIN cookie middleware (Microsoft.Owin.Security.Cookies 3.0.0, `LoginPath=/default.aspx`) rewrites a 401 to a **302** to `default.aspx?ReturnUrl=<PathBase>/api/BugFromEmail` for any non-AJAX request, meaning one without `X-Requested-With: XMLHttpRequest`.

Asserted:
- One redirect.
- Final path `default.aspx`.
- The decoded `ReturnUrl` relative to the base is `api/bugfromemail` (N3).
- No bugs.

This behavior comes from the framework's documented default (Katana `CookieAuthenticationProvider.ApplyRedirect`), not from BugTracker source. It is pinned because a port that answers 401 instead would break callers that follow redirects identically.

### 2. `missingFromAddressIsBadRequest`

A JSON body without `FromAddress` gives **400** with `{"Message":"The request is invalid.","ModelState":{"bugFromEmail.FromAddress":["The FromAddress field is required."]}}`. The judge compares the `Message` value, the exact set of ModelState keys, and the first message. No rows are written.

The texts are Web API 5.2.3 / DataAnnotations defaults. The key is prefixed with the action's parameter name, `bugFromEmail`.

### 5. `mimeMessageFromServiceCreatesBug` (inherited newline mix)

The request has exactly the client's shape: form `projectId=1`, `fromAddress`, a `shortDescription` (overridden), and `message` set to:
```
From: Reporter Person <reporter@example.com>
To: support@example.com
Subject: Printer is on fire
MIME-Version: 1.0
Content-Type: text/plain; charset=us-ascii

It is really on fire.
```
All line breaks are CRLF, and the body has no trailing newline.

Expected:
- **`bg_short_desc`** is the MIME subject, `Printer is on fire` (:97-109).
- **`bp_comment`** is `"Subject: Printer is on fire\nTo: support@example.com\n" + "\r\n" + "It is really on fire."`. The header block is built at Mail/Mime.cs:234-256, Environment.NewLine is added at :40, and the body comes from FindFirstPlainTextVersion at Mime.cs:99-122.
- **`bp_email_from`** is `reporter@example.com`, the parsed address (:43).
- **`bp_email_cc`** is `''`.
- No file posts.

Note that the body text comes from OpenPop's `GetBodyAsText`. The judge assumes the body is exactly the bytes after the blank line. This is a library behavior, to confirm in the validation run.

### 6. `mimeReplyWithTrackingIdAppendsComment`

The test seeds bug 1. The subject is `Re: Bug:1 was added - Seeded bug (DO NOT EDIT THIS:1)`, and `get_bugid_from_subject` returns 1 (Mime.cs:27-68).

Expected:
- 200, body `1`.
- There is still one bug, with its description and status unchanged.
- One `received` post with comment `"Subject: <subject>\nTo: support@example.com\n\r\nThanks, fixed."`, from `reporter@example.com`, and cc `''`.
- `bg_last_updated_user` is admin, and `bg_last_updated_date` = `bp_date`.

### 7. `jsonBugIdAppendsOrFallsBackToNewBug`

The test seeds bug 1.
- **`BugId=1`** with no `Message` returns body `1` and creates one `received` post `More info` on bug 1.
- **`BugId=99`**, a bug that doesn't exist, returns body `2`. A new bug 2 is created with `Orphan reply` and its own `received` post. There's no bug 99 (:72-88).

### 8. `jsonAttachmentIsStored` (inherited)

The test sends a base64 `Attachment` with the 261-byte payload, `AttachmentFileName=mail.bin`, `AttachmentContentType=application/x-judge` and `AttachmentDescription=from mail`.

Expected:
- One `file` post with `bp_file` = `mail.bin`, `bp_comment` = `from mail`, `bp_size` = 261, the content type as given, **`bp_parent` NULL**, and the blob byte-equal to the payload.
- One `received` post.
- `bugs.bg_last_updated_date` = the file post's `bp_date`.

The non-MIME path passes parent −1 (:158-168). MIME attachments get the comment's post id instead (:149, Mime.cs:181-186), so the two paths are inconsistent.

## Normalization beyond README

- **Dates** use a window from the DB clock (`getdate()`), as in S3.
- **The response body is trimmed** before it is compared to the id. JSON whitespace is not data.
- **Only the media type of `Content-Type` is compared.**

## Not judged, and why

- **MIME attachments, multipart, and HTML-only bodies** would depend on OpenPop parsing details that can't be verified without running.
- **The auto reply e-mail** is skipped by the seed (no project e-mail). Sending SMTP isn't observable.
- **Truncation of descriptions longer than 200 characters** (:24-27, :104-107) isn't covered.
- **The real client's `api/Login` step** is S1's surface. The judge uses the shared login fixture, which yields the same cookie.
- **The forced-project override** (:122-125) would need a non-admin user. Non-admin login is S1's concern; see the report on `Security.cs:117`.
