# S4 — Attachments

Test class: `judge/src/test/java/judge/scenarios/S4_AttachmentTest.java`. Lines are relative to `src/BugTracker.Web/`.

## Settings relied on (Web.config)

- `StoreAttachmentsInDatabase=1`. Content goes into `bug_post_attachments.bpa_content` and is asserted there (btnet/bug.cs:347-372). The filesystem branch isn't exercised.
- `UploadFolder=App_Data\uploads`. Global.asax.cs:88-92 creates it at startup, so `get_upload_folder()` (btnet/util.cs:614-635), which runs unconditionally, does not throw.
- `MaxUploadSize=5000000`, and `maxRequestLength=51200` KB is larger than that.
- `EnableInternalOnlyPosts=0`, so `internal_only` isn't rendered.

The seeded bug is bug 1 in project 1. Seeded attachments are `bug_posts` bp_id 1 plus a blob.

## Handles (binding on the port)

- **`add_attachment.aspx?id=N`** is a multipart form with these logical fields:
  - `desc`
  - `attached_file` (type file)
  - submit button `sub`
- **Result message.** The original answers with exactly
  `<script>function foo() {parent.set_msg('MSG'); [parent.opener.rewrite_posts(N)]}</script><html><body onload='foo()'></body></html>`
  (add_attachment.aspx.cs:142-159). The judge requires only that the exact `MSG` text appears in the response body. The UI around it may be redesigned.
- **`view_attachment.aspx?id=<bp_id>&bug_id=<bug>[&download=0]`**: the judge reads the status, the media type of `Content-Type`, the exact `Content-Disposition` value, and the body bytes.

### 6. `downloadReturnsStoredBytes`

The test seeds `seed.bin` with content type `application/octet-stream` and 261 bytes.

`GET view_attachment.aspx?id=1&bug_id=1`:
- 200.
- The media type is `application/octet-stream`.
- `Content-Disposition` is exactly `attachment; filename="seed.bin"` (:121-124). `download` is absent, which means download.

With `&download=0`, `Content-Disposition` is `inline; filename="seed.bin"`.

The body starts with the stored bytes, byte-for-byte, followed only by CR/LF bytes (see "Not judged").

## Normalization beyond README

- **Content-Type** is compared on its media type only; the charset parameter is ignored. ASP.NET's charset suffix depends on framework defaults, not on source.
- **Trailing whitespace after the download body (not judged).** `view_attachment.aspx` writes the blob in `Page_Load` without `Response.End`, so the page's literal text renders after the bytes. That literal text is the newlines after the directives, the newlines from the `#include` of inc.aspx, and the `\n\n` after `</script>`. By reading the files, this is 13 LF in this checkout; a CRLF deployment would differ.

  The exact count depends on ASP.NET's literal handling and on the deployed file's line endings, neither of which can be confirmed without running. So the judge requires an exact byte-for-byte prefix and allows only CR/LF after it. The port may return exactly the bytes. This is a suspected defect: downloads are corrupted by trailing newlines.

## Not judged, and why

- **The filesystem storage branch:** it is off by configuration, and the judge can't see the server's disk.
- **The `internal_only` checkbox:** it is hidden by configuration.
- **Notifications on upload** (`send_notifications`, btnet/bug.cs:412-415): the seed has no subscribers.
- **Response caching headers** (`do_not_cache`, `SetExpires` +3 days for inline): these are time-dependent and plumbing.
