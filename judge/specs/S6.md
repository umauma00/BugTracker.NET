2 projects, 5 categories, project_user_xref rows for users 7, 8, 9 (setup.sql:427-432), no bugs.

## Fixtures and priming

- `loginAdmin` (core fixture).
- `primeAspNetSession(web)` (core fixture in `judge.core.Scenario`, shared with S3/S4): one search postback (`search.aspx`, `hit_submit_button=1`)
  before any admin postback. `edit_user`, `delete_user`, `edit_category`, … set
  `ViewStateUserKey = Session.SessionID` (e.g. edit_user.aspx.cs:20). An empty
  InProc session gets a new id per request, which would fail view-state
  validation on the postback; search.aspx.cs:620 stores `Session["bugs"]`, making
  the session stick. Read-only, harmless on the port. *(Reading of ASP.NET
  session-cookie mechanics — to be confirmed when the original runs.)*
- Fixture bug (only in `deleteUserReferencedByBugIsRefused`), written like bug.cs:823-849.
- Every textarea is set explicitly (`signature`, `desc`, `custom_dropdown_values1..3`)
  so a leading newline in rendered textarea markup cannot leak into the DB.

## Normalization beyond N1–N3

- Logical element id (`#x` or `#ctl00_body_x`), as in S1.
- Table data rows: rows of `th` only, or of `td class="datah"` only, are headings and
  skipped — sortable_html_table.cs:109-127 writes its heading row as `td.datah`.

## Not judged, and why

- **Non-admin access to admin pages while logged in**: no non-admin can sign in in
  the original (S1 test 8: `GetIdentity` crash), so the project-admin branches
  (edit_user.aspx.cs:32-53, delete_user.aspx.cs:24-40, users.aspx:65-101) are unreachable.
  Only anonymous access is judged (tests 2, 3).
- Priorities/statuses/orgs edit pages (same pattern as categories; representative set only).
- Exact `us_salt` / `us_password` values (random salt). Password hash correctness is
  judged through login (test 7).
- Admin "Server Info" block and the donation nag (machine-specific / needs >100 bugs).
- "Recreate Search Index" button (needs Elasticsearch).
