# S2 — Bug list page and query API

Test class: `judge/src/test/java/judge/scenarios/S2_BugListTest.java`.

## Schema fixture (deviation from "seed only from setup.sql" — needs review)

The original reads `queries` through Entity Framework, and the mapping includes
`qu_columns` (`Models/Mapping/queryMap.cs:29`, used by `Models/query.cs:17-24`).
**setup.sql does not create that column** (`setup.sql:697-705`). The database
project does (`src/BugTracker.Database/dbo/Tables/queries.sql:8`, default
`'ColumnsNeeded'`), and its `Script.PostDeployment.sql` rewrites 8 of the 10
seeded queries with SQL the API can run plus a column list. On a setup.sql-only
database every EF read of `queries` fails (bugs.aspx, api/BugQuery, print_bugs*),
and setup.sql's own query SQL could not run under the API anyway (unnamed first
column and `ORDER BY` inside a derived table).

So each S2/S7 test, after `Db.reset()`, runs
`alter table queries add qu_columns nvarchar(max) not null default 'ColumnsNeeded'`
and then executes `src/BugTracker.Database/Script.PostDeployment.sql` verbatim
(`S2_BugListTest.applyDatabaseProjectQueries`). This reproduces the schema the
original actually runs on. Proposed core change: do this in `Db.reset()` for all
scenarios (see report).

## API: `GET api/BugQuery` (binding)

Route `api/{controller}` (WebApiConfig.cs:203-207), `[Authorize]`
(BugQueryController.cs:6). Query parameters, all required by the action
signature (BugQueryController.cs:9): `queryId`, `sortBy`, `sortOrder`, `start`,
`length`, `idOnly`, and `filters[i][Column]` / `filters[i][Value]` — the jQuery
`$.param` encoding the page sends (BugList.ascx:140-173; the same keys are parsed
explicitly in print_bugs.aspx.cs:62-75). Request sent with `Accept: application/json`.

Response 200, JSON object with properties in this order:
`recordsTotal` (int), `recordsFiltered` (int), `data` (array) — BugQueryController.cs:20-25.
Each `data` element is one row of `SELECT t.*` (BugQueryExecutor.cs:71,85): property
names = the query's column aliases, in query order; for query 1:
`$COLOR, id, $FLAG, desc, project, organization, category, reported by, reported on,
priority, assigned to, status, last updated by, last updated on`
(Script.PostDeployment.sql:13-16). Values: ints as JSON integers, strings, SQL NULL as
`null`, `datetime` as `"yyyy-MM-ddTHH:mm:ss"` without offset (Json.NET default for
`DateTimeKind.Unspecified`; fixtures use whole seconds so no fraction is emitted).
`$COLOR` = `isnull(pr_background_color,'transparent')`; `$FLAG` = current user's
`bug_user.bu_flag` or 0.

## bugs.aspx (binding handles)

- `select` with logical name **`query`**: one option per query visible to the user
  (user/org null or matching), ordered by description, text = `qu_desc`, value = `qu_id`;
  selected = `?queryId` if given, else the `qu_default = 1` query (bugs.aspx.cs:149-172,
  Context.cs:42-50). Expected order/value list is in the test. Title `BugTracker.NET - bugs`.
- `table#bug-table`: first row = visible columns (query columns minus `$COLOR`/`$SCORE`,
  `$FLAG`→`flag`, `$SEEN`→`new`, `$VOTE`→`votes`); second row = filters; no data rows
  server-side (BugList.ascx:3-30, BugList.ascx.cs:204-222).
- `select.table-filter[data-column-name=<column>]` for each filterable visible column
  (`$FLAG $SEEN project organization category priority status reported by assigned to`),
  first option `value="" [no filter]`, then fixed lists ($FLAG 0 None/1 Red/2 Green) or
  names from the lookup table ordered by name, value = text (BugList.ascx.cs:224-327).
  `data-column-name` is binding: it is the `Column` the client puts in `filters`.

## Normalization beyond N1–N3

- **Row order inside `data` is not judged** (rows compared sorted by id). The outer
  `SELECT t.* … WHERE id IN (… ORDER BY … OFFSET … FETCH …)` has no ORDER BY
  (BugQueryExecutor.cs:85-109), so SQL Server does not define it. Which rows form the
  page *is* judged. (Suspected defect, not pinned: the grid can show a page in the wrong order.)
- `Location` of the login redirect: only its path (`default.aspx`) is judged; the
  return-URL parameter carries the deployment base path.

## Inherited quirks pinned

- Lowercase `asc` → descending (BugQueryExecutor.cs:133), i.e. the bug list never sorts ascending from the UI.

## Not judged, and why

- Unencoded vs jQuery-bracket filter binding in Web API (`filters[0][Column]`): the tests send
  the bracket form the page sends; whether Web API 2's `[FromUri] BugQueryFilter[]` binds it
  could not be verified without running the original — **first thing to check in validation**.
- Exact JSON date fraction formatting for non-zero milliseconds (fixtures avoid it).
- Non-admin visibility (project/org permission rewriting): non-admin login is broken in the
  original (Security.cs:117 reads an unselected `project_admin` column) — belongs to S1.
- The JS rendering of cells (dates via moment, flag classes) — client side.
- `bugs.aspx?queryId=<unknown>` (DropDownList throws) — error page content.
